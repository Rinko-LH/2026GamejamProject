# 跨系统整合手册

> 配套《系统实施规范.md》：规范回答"单个系统怎么建"，本手册回答"多个系统怎么合"——
> 批次递进、装配节号切分、并行冲突对策、检查点、风险登记。
>
> 原则：**任何两个系统不允许同时改同一个文件的同一区域**；所有场景变更只走
> `DrawingBoardSetup` 节号；每批合完必须过该批检查点再开下一批。

## 2. 装配节号切分（DrawingBoardSetup.cs）

场景只由装配菜单改。每个系统独占节号，重跑菜单互不覆盖：

| 节号 | 内容 | 所属系统 | 状态 |

- 新系统**只准在自己节号里加代码**，禁止改别家节号（改=合并冲突）；

- 跑菜单前确认编辑器在编辑态（铁律 R8）。

## 6. 合并操作手册（两人改同一仓库时）

1. **拉代码前先看节号**：`DrawingBoardSetup.cs` 的 diff 只应涉及自己的节号；越界即冲突，退回改设计不硬合；
2. **场景文件冲突**：TestScene.unity 冲突**不手合**——以装配菜单为准：接受对方版本 → 重跑自己节号 → 重跑全菜单 → CP 验证；
3. **接口变更**：Contracts 下接口只准加成员不准改签名（改签名=全批阻塞）；必须改时先升"契约修订"议题，全批同步；
4. **提交粒度**：一个系统一个 commit（`feat(s1): ...`），场景与代码同 commit；整合回归单独 commit（`feat(s12): ...`）；
5. **验证留痕**：每批检查点结果写进 `docs/阶段一-变更留档.md`（批次小节），失败项带 console 原文。

## 7. 执行模式决议（2026-10-17，D8）

**决议：单会话「批内准并行」，不物理多开对话。**

- **流程**：代码按目录隔离连续写（S1→`UI/`、S2→`World/`、S3~S6→`Quest/`、S8→`Mood/`、S9/S10→`Ending/`）→ 一次 refresh + 编译修复 → 按节号连续跑装配菜单 → 单次 execute_code 全链回归 → 提交；
- **不采用物理多对话并行的原因**：Unity Editor 单实例共享（play/stop 互相破坏编辑态，R8/K1）、场景文件整体存盘（并行 SaveScene 互相覆盖）、域重载（他人 execute_code 读旧域快照）、无法给其他会话加锁、协调成本 ≥ 并行收益；
- **批内顺序**：批 1 = S2 → S3 → S1（调试 HUD 留到 S1 最后删，便于 S2/S3 验证）；批 2~3 同模式；**批 4（S9→S10 串行依赖）与批 5（S12 全链路回归）必须单会话**；
- **收口**：每批 CP 检查点由主持会话统一验证，结果写 `docs/阶段一-变更留档.md`；
- **未来多人/多 Agent 协作**：仍按 §6 合并手册 + 节号切分执行，Unity 同时只允许一个会话持有。
